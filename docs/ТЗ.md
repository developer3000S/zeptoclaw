# Техническое задание  
## Система: Децентрализованная P2P-сеть агентов на основе PicoClaw  
### Условное наименование: **PicoClaw Agent Mesh**
### Версия документа: **0.1**

---

## 1. Общие сведения

### 1.1. Наименование проекта

Разработка программной системы **«PicoClaw Agent Mesh»** — полностью децентрализованной одноранговой сети автономных агентов на базе проекта **PicoClaw**, предназначенной для распределенного приема, маршрутизации, декомпозиции и выполнения задач между физически распределенными серверами.

### 1.2. Назначение системы

Система предназначена для объединения 100 и более агентов PicoClaw, запущенных на разных серверах, в единую децентрализованную сеть без обязательного центрального координатора.

Система должна обеспечивать:

- прием задачи на любом узле сети;
- поиск исполнителей среди соседей узла;
- рекурсивное делегирование задачи соседям соседей;
- выполнение задач локальными экземплярами PicoClaw;
- возврат результатов инициатору задачи;
- отказоустойчивость при падении отдельных узлов;
- безопасное взаимодействие между узлами через локальную сеть и Интернет.

### 1.3. Цель разработки

Создать программный слой децентрализованной агентной сети, который:

1. Использует PicoClaw в качестве исполнительного AI-агента.
2. Обеспечивает P2P-взаимодействие между узлами.
3. Позволяет масштабировать систему до сотен и тысяч узлов.
4. Не требует постоянного центрального сервера управления.
5. Поддерживает работу в локальной сети, через Интернет и в смешанной топологии.
6. Обеспечивает наблюдаемость, безопасность и администрируемость.

### 1.4. Область применения

Система может применяться для:

- распределенных AI-ассистентов;
- автономных агентов автоматизации;
- распределенного выполнения исследовательских и инженерных задач;
- внутренних корпоративных агентных сетей;
- отказоустойчивых систем обработки задач без единой точки отказа.

## 2. Термины и определения

В настоящем документе используются следующие термины:

### 2.1. Узел

Программно-аппаратная единица системы, запущенная на отдельном сервере или в контейнере, включающая:

- один или несколько экземпляров PicoClaw;
- mesh-демон;
- локальное хранилище;
- сетевой агентский интерфейс;
- компоненты безопасности и телеметрии.

### 2.2. Пир

Сетевая идентичность узла в P2P-сети, имеющая уникальный криптографический идентификатор.

### 2.3. Агент

Экземпляр PicoClaw, способный выполнять задачи с использованием моделей, инструментов и навыков.

### 2.4. Сосед

Пир, с которым данный узел поддерживает активное или потенциальное прямое соединение.

### 2.5. Задача

Единица работы, поступающая в сеть и подлежащая выполнению одним или несколькими агентами.

### 2.6. Подзадача

Часть исходной задачи, выделенная узлом для делегирования другому узлу.

### 2.7. Навык

Декларируемая способность агента или узла выполнять определенный тип задач.

Примеры:

- `coding`;
- `research`;
- `summarization`;
- `web-search`;
- `shell-automation`;
- `data-analysis`.

### 2.8. TTL

Time-To-Live — предельное количество переходов задачи или служебного сообщения по сети.

### 2.9. Route Stack

Список узлов, через которые прошла задача, используемый для возврата результата.

### 2.10. DHT

Распределенная хеш-таблица, используемая для поиска узлов по ключам, например по навыкам.

### 2.11. Gossip

Протокол эпидемического распространения информации о состоянии узлов.

### 2.12. Bootstrap-узел

Необязательный узел, используемый для первоначального подключения нового участника к сети.

## 3. Исходные данные и ограничения

### 3.1. Базовая технология

Исполнительным компонентом агента является проект **PicoClaw**.

Система должна использовать PicoClaw как основной агентский рантайм и не должна требовать обязательной глубокой модификации его ядра на первом этапе.

### 3.2. Допущения

1. Узлы работают преимущественно под управлением Linux.
2. Узлы могут находиться в локальной сети, за NAT или иметь публичный адрес.
3. Количество узлов в первой целевой версии — от 100 до 1000.
4. Задачи могут быть асинхронными и занимать от секунд до десятков минут.
5. Не требуется блокчейн, майнинг, токены или публичная децентрализованная экономика.
6. Система не должна требовать обязательного центрального сервера после развертывания.
7. Наличие одного или нескольких временных bootstrap-узлов допускается для первичного подключения.

### 3.3. Ограничения

1. Не гарантируется строгая глобальная консистентность состояния всех агентов.
2. Не требуется выполнение задач в реальном времени с жесткими гарантиями задержек.
3. Модельные API-ключи должны оставаться на локальных узлах и не передаваться по сети.
4. Задачи, требующие доступа к локальным ресурсам узла, должны выполняться только на этом узле или с явного разрешения оператора.

## 4. Требования к системе в целом

## 4.1. Архитектурная модель

Система должна строиться по децентрализованной P2P-архитектуре.

Каждый узел должен выполнять следующие роли:

1. Участник P2P-сети.
2. Локальный исполнитель задач.
3. Маршрутизатор чужих задач.
4. Агрегатор результатов собственных подзадач.
5. Источник телеметрии и локального аудита.

### 4.1.1. Отсутствие обязательного центрального координатора

Система должна сохранять работоспособность при отсутствии центрального сервера.

Допускаются необязательные компоненты:

- bootstrap-узлы для первичного подключения;
- relay-узлы для помощи в соединении через NAT;
- мониторинговые сервисы;
- локальные административные API.

Однако ни один из этих компонентов не должен быть обязательным для работы уже сформированной сети.

### 4.1.2. Структура узла

Каждый узел должен содержать следующие логические компоненты:

```text
PicoClaw Agent Mesh Node
│
├── Mesh Daemon
│   ├── Peer Identity
│   ├── Transport Layer
│   ├── Discovery Layer
│   ├── Routing Layer
│   ├── Task Manager
│   ├── Capability Registry
│   ├── Security Layer
│   └── Telemetry
│
├── PicoClaw Adapter
│   ├── Process Manager
│   ├── Agent Invoker
│   ├── Workspace Manager
│   └── Result Collector
│
├── Local Storage
│   ├── Peer Store
│   ├── Task Store
│   ├── Artifact Store
│   ├── Audit Log
│   └── Key Store
│
└── Admin Interface
    ├── REST API
    ├── CLI
    └── Config Files
```

## 6. Функциональные требования

## 6.1. Идентификация узла

### 6.1.1. Генерация идентификатора

Каждый узел при первом запуске должен генерировать криптографическую пару ключей:

- приватный ключ Ed25519;
- публичный ключ, из которого формируется `Peer ID`.

### 6.1.2. Хранение ключей

Приватный ключ должен храниться в локальном защищенном каталоге узла.

Рекомендуемое расположение:

```text
/var/lib/picomesh/keys/peer.key
```

Права доступа должны быть не шире `0600`.

### 6.1.3. Идентификатор узла

Каждый узел должен иметь устойчивый идентификатор:

```text
peer_id = base58/ed25519 public key derived ID
```

Идентификатор не должен меняться между перезапусками узла, если не выполнена процедура перегенерации ключа.

---

## 6.2. Регистрация возможностей узла

Каждый узел должен поддерживать декларирование собственных возможностей.

### 6.2.1. Структура возможностей

Пример:

```json
{
  "peer_id": "12D3KooW...",
  "version": "0.1.0",
  "capabilities": {
    "skills": [
      "research",
      "coding",
      "summarization"
    ],
    "max_parallel_tasks": 4,
    "models": [
      "gpt-4",
      "claude-sonnet",
      "local-llm"
    ],
    "resource_class": "medium",
    "accept_external_tasks": true
  },
  "address_info": {
    "lan": true,
    "wan": true,
    "relay_capable": false
  }
}
```

### 6.2.2. Обновление возможностей

Узел должен иметь возможность обновлять набор навыков без перезапуска сети.

### 6.2.3. Ограничение навыков

Администратор узла должен иметь возможность явно разрешать или запрещать определенные навыки.

---

## 6.3. Обнаружение соседей

Система должна поддерживать многоуровневое обнаружение соседей.

---

### 6.3.1. Обнаружение на одном сервере

Если на одном физическом или виртуальном сервере запущено несколько узлов системы, они должны находить друг друга без обращения к внешним сетевым сервисам.

Требуемый механизм:

- локальный каталог регистрации;
- Unix domain sockets;
- общий локальный реестр.

Пример каталога:

```text
/var/run/picomesh/local/
├── node-1.sock
├── node-2.sock
├── node-3.sock
└── registry.json
```

Требования:

1. Узел при запуске должен регистрировать себя в локальном реестре.
2. Узел должен обнаруживать другие локальные узлы.
3. Локальное соединение должно быть предпочтительнее сетевого.
4. При завершении работы узел должен удалять свою запись или помечать ее неактивной.

---

### 6.3.2. Обнаружение в локальной сети

Для узлов, находящихся в одной LAN, система должна поддерживать автоматическое обнаружение.

Требуемый механизм:

- mDNS;
- анонсирование сервиса;
- поиск сервисов по имени, например `_picomesh._tcp.local`.

Требования:

1. Узел должен анонсировать себя в локальной сети.
2. Узел должен обнаруживать другие узлы без ручной настройки.
3. Должна поддерживаться работа в IPv4 и, по возможности, IPv6.
4. При обнаружении узла система должна проверять его криптографический идентификатор перед добавлением в соседи.

---

### 6.3.3. Обнаружение между серверами через Интернет

Для удаленных серверов система должна поддерживать следующие механизмы:

#### 6.3.3.1. Bootstrap-узлы

Новый узел должен иметь возможность подключиться к одному или нескольким заранее известным узлам.

Пример конфигурации:

```yaml
bootstrap:
  - "/dns4/bootstrap-1.example.net/tcp/4001/p2p/12D3KooW..."
  - "/dns4/bootstrap-2.example.net/tcp/4001/p2p/12D3KooW..."
```

Bootstrap-узлы не являются обязательными для работы уже подключенных узлов.

#### 6.3.3.2. Peer Exchange

Узлы должны обмениваться информацией о доступных соседях, если это разрешено политикой безопасности.

#### 6.3.3.3. Kademlia DHT

Система должна поддерживать DHT для поиска:

- узлов по навыкам;
- узлов по идентификатору задачи;
- узлов по идентификатору результата;
- служебных ключей сети.

#### 6.3.3.4. Relay-узлы

Для узлов за NAT должна поддерживаться возможность соединения через реле.

Требования:

1. Реле не должно читать содержимое зашифрованных сообщений.
2. Использование реле должно быть опциональным.
3. Реле должно ограничивать пропускную способность и число соединений.
4. Узел должен предпочитать прямое соединение реле-соединению.

---

## 6.4. Таблица соседей

Каждый узел должен поддерживать ограниченную таблицу соседей.

### 6.4.1. Размер таблицы

Рекомендуемые параметры:

```yaml
neighbors:
  min: 8
  target: 16
  max: 64
```

### 6.4.2. Категории соседей

Соседи должны разделяться на категории:

1. `local` — узлы на том же сервере.
2. `lan` — узлы в локальной сети.
3. `wan` — узлы через Интернет.
4. `bootstrap` — узлы первоначального подключения.
5. `trusted` — доверенные узлы.
6. `untrusted` — ограниченно доверенные узлы.

### 6.4.3. Оценка соседей

Для каждого соседа должны накапливаться метрики:

- задержка;
- количество успешных задач;
- количество ошибок;
- время жизни соединения;
- нагрузка;
- рейтинг доверия.

### 6.4.4. Исключение соседей

Узел должен исключать соседей, если:

- они недоступны дольше заданного времени;
- от них получено большое количество ошибочных ответов;
- нарушена подпись сообщений;
- зафиксировано превышение лимитов;
- узел помечен администратором как нежелательный.

---

## 6.5. Поддержание членства в сети

Система должна использовать gossip-механизм для поддержания информации о живых узлах.

### 6.5.1. Данные членства

Каждый узел должен распространять о себе следующую информацию:

```json
{
  "peer_id": "12D3KooW...",
  "timestamp": 1780000000,
  "skills": ["coding", "research"],
  "load": 0.42,
  "max_parallel_tasks": 4,
  "version": "0.1.0",
  "status": "active"
}
```

### 6.5.2. Распространение

Gossip-сообщения должны передаваться случайным соседям с заданной периодичностью.

Рекомендуемая периодичность:

- служебный heartbeat: 1–5 секунд;
- полная синхронизация возможностей: 30–120 секунд.

### 6.5.3. Обнаружение отказа

Узел должен считать соседний узел недоступным, если от него нет подтверждения в течение заданного таймаута.

Рекомендуемое значение:

```text
failure_timeout = 15 секунд
```

## 6.6. Работа с задачами

### 6.6.1. Источник задачи

Задача может поступить:

1. Через локальный административный интерфейс узла.
2. Через локальный пользовательский интерфейс.
3. Через другой узел сети.
4. Через запланированный триггер на узле.

### 6.6.2. Формат задачи

Задача должна быть представлена в виде стандартизированного конверта.

Пример логической структуры:

```json
{
  "task_id": "01J8...",
  "parent_task_id": null,
  "origin_peer_id": "12D3KooW...",
  "sender_peer_id": "12D3KooW...",
  "created_at": "2026-09-12T10:00:00Z",
  "ttl": 5,
  "priority": 5,
  "required_skills": ["research", "summarization"],
  "payload": {
    "instruction": "Собрать информацию о ...",
    "context_digest": "sha256:...",
    "attachments": []
  },
  "constraints": {
    "max_duration_seconds": 600,
    "allow_network_tools": true,
    "allow_shell": false
  },
  "route_stack": [],
  "signature": "base64..."
}
```

### 6.6.3. Идентификатор задачи

Каждая задача должна иметь глобально уникальный идентификатор.

Рекомендуемый формат:

```text
ULID или UUIDv7
```

### 6.6.4. Подпись задачи

Задача должна быть подписана отправителем.

Подпись должна покрывать:

- `task_id`;
- `parent_task_id`;
- `origin_peer_id`;
- `sender_peer_id`;
- `payload_hash`;
- `ttl`;
- `created_at`.

### 6.6.5. Дедупликация

Каждый узел должен хранить кеш недавно обработанных идентификаторов задач.

Минимальный срок хранения записи дедупликации:

```text
15 минут
```

При повторном получении задачи с тем же `task_id` узел не должен выполнять ее повторно, если не получил явный запрос на повтор.

---

## 6.7. Жизненный цикл задачи

Система должна поддерживать следующие состояния задачи:

```text
RECEIVED
VALIDATING
EVALUATING
ACCEPTED
REJECTED
FORWARDED
RUNNING
WAITING_SUBTASKS
AGGREGATING
COMPLETED
FAILED
TIMEOUT
CANCELED
```

### 6.7.1. RECEIVED

Задача получена узлом.

### 6.7.2. VALIDATING

Проверяются:

- подпись;
- формат;
- TTL;
- права отправителя;
- наличие обязательных полей;
- отсутствие дубля.

### 6.7.3. EVALUATING

Узел оценивает:

- наличие навыков;
- текущую загрузку;
- доступность PicoClaw;
- лимиты безопасности;
- возможность выполнить задачу локально.

### 6.7.4. ACCEPTED

Узел принял задачу к исполнению.

### 6.7.5. REJECTED

Узел отклонил задачу.

Причина отклонения должна быть указана в служебном ответе.

### 6.7.6. FORWARDED

Задача передана другому узлу.

### 6.7.7. RUNNING

Локальный PicoClaw выполняет задачу.

### 6.7.8. WAITING_SUBTASKS

Узел ожидает результаты подзадач.

### 6.7.9. AGGREGATING

Узел агрегирует результаты.

### 6.7.10. COMPLETED

Задача успешно завершена.

### 6.7.11. FAILED

Задача завершилась ошибкой.

### 6.7.12. TIMEOUT

Задача не завершена в отведенное время.

### 6.7.13. CANCELED

Задача отменена инициатором или администратором.

---

## 6.8. Локальное выполнение задачи

Если узел принимает задачу, он должен выполнить ее через PicoClaw Adapter.

### 6.8.1. Запуск агента

Адаптер должен уметь:

1. Запускать PicoClaw с заданной конфигурацией.
2. Передавать текст задачи.
3. Передавать разрешенные навыки.
4. Передавать рабочее пространство.
5. Получать результат выполнения.
6. Ограничивать время выполнения.

### 6.8.2. Изоляция

Каждая задача должна выполняться в изолированном рабочем каталоге.

Пример:

```text
/var/lib/picomesh/tasks/<task_id>/workspace
```

### 6.8.3. Таймаут

Для каждой задачи должен задаваться таймаут.

Значение по умолчанию:

```text
600 секунд
```

Максимально допустимое значение должно быть настраиваемым.

### 6.8.4. Ограничение ресурсов

Узел должен ограничивать:

- максимальное число одновременных задач;
- максимальное время выполнения;
- максимальный объем дискового пространства;
- максимальный объем памяти процесса;
- сетевой доступ, если он не разрешен.

---

## 6.9. Делегирование задачи

Если узел не может выполнить задачу самостоятельно, он должен иметь возможность делегировать ее.

### 6.9.1. Локальная декомпозиция

Узел может разбить задачу на подзадачи.

Пример:

```text
Исходная задача:
  Подготовить отчет по рынку и написать код для анализа.

Подзадачи:
  1. research: собрать данные.
  2. coding: написать скрипт анализа.
  3. summarization: подготовить итоговый отчет.
```

### 6.9.2. Выбор исполнителя

Выбор узла-исполнителя должен основываться на:

- совпадении навыков;
- рейтинге доверия;
- текущей нагрузке;
- сетевой задержке;
- истории успешных выполнений;
- доступности узла.

Рекомендуемая формула оценки:

```text
score =
  skill_match * 0.40 +
  trust_score * 0.25 +
  available_capacity * 0.20 +
  latency_score * 0.10 +
  success_rate * 0.05
```

### 6.9.3. Ограничение глубины делегирования

Каждая задача должна иметь параметр `ttl`.

При каждом делегировании `ttl` уменьшается на 1.

Если `ttl <= 0`, задача не может быть делегирована дальше.

Рекомендуемые значения:

```text
default_ttl = 5
max_ttl = 10
```

### 6.9.4. Ограничение ширины рассылки

Узел не должен рассылать одну задачу всем соседям одновременно без необходимости.

Требуемые ограничения:

```yaml
forwarding:
  max_parallel_candidates: 3
  max_fanout: 5
  retry_interval_seconds: 5
```

### 6.9.5. Механизм поиска исполнителя

Порядок поиска исполнителя:

1. Проверить локальные возможности.
2. Проверить таблицу соседей.
3. Проверить кеш известных узлов с нужными навыками.
4. Выполнить запрос к DHT.
5. При необходимости опубликовать запрос в тематический P2P-топик.
6. Если исполнитель не найден, вернуть ошибку инициатору.

---

## 6.10. Возврат результата

### 6.10.1. Возврат через маршрут

Если задача прошла через несколько узлов, результат должен возвращаться по сохраненному маршруту.

Пример:

```text
A -> B -> C -> D
D -> C -> B -> A
```

### 6.10.2. Прямой возврат

Если исполнитель может установить прямое соединение с инициатором, допускается прямой возврат результата.

### 6.10.3. Подпись результата

Результат должен быть подписан узлом-исполнителем.

### 6.10.4. Формат результата

Пример:

```json
{
  "task_id": "01J8...",
  "worker_peer_id": "12D3KooW...",
  "status": "COMPLETED",
  "result": {
    "text": "Итоговый результат...",
    "artifacts": [
      {
        "name": "report.md",
        "hash": "sha256:...",
        "size": 12045
      }
    ]
  },
  "started_at": "2026-09-12T10:00:05Z",
  "finished_at": "2026-09-12T10:02:11Z",
  "signature": "base64..."
}
```

### 6.10.5. Агрегация

Если задача была разделена на подзадачи, узел-агрегатор должен:

1. Дождаться результатов подзадач.
2. Проверить их статус.
3. При необходимости выполнить повтор.
4. Объединить результаты.
5. Подписать итоговый результат.
6. Вернуть результат инициатору.

---

## 6.11. Отмена задач

Система должна поддерживать отмену задач.

### 6.11.1. Источник отмены

Отмена может быть инициирована:

- пользователем;
- администратором;
- узлом-инициатором;
- по таймауту;
- по политике безопасности.

### 6.11.2. Распространение отмены

Сообщение об отмене должно содержать:

```json
{
  "task_id": "01J8...",
  "origin_peer_id": "12D3KooW...",
  "reason": "user_canceled",
  "signature": "base64..."
}
```

### 6.11.3. Обработка отмены

Узел, получивший отмену, должен:

1. Прекратить делегирование задачи.
2. Попытаться остановить локальный процесс выполнения.
3. Пометить задачу как `CANCELED`.
4. Уведомить известные дочерние узлы.

---

## 6.12. Обработка ошибок

Система должна классифицировать ошибки:

1. Ошибки валидации.
2. Ошибки безопасности.
3. Ошибки исполнения.
4. Ошибки сети.
5. Таймауты.
6. Отсутствие исполнителя.
7. Превышение лимитов.

### 6.12.1. Повторные попытки

Повторные попытки допускаются для:

- сетевых сбоев;
- временной недоступности исполнителя;
- таймаутов соединения.

Не должны автоматически повторяться:

- ошибки безопасности;
- ошибки подписи;
- ошибки валидации;
- задачи, явно отклоненные политикой.

### 6.12.2. Идемпотентность

Исполнители должны учитывать, что задача может быть доставлена повторно.

Для этого используется:

- `task_id`;
- локальный журнал выполненных задач;
- проверка состояния задачи перед запуском.

---

## 7. Требования к сетевому взаимодействию

## 7.1. Транспорт

Система должна поддерживать:

```text
QUIC over UDP
TCP fallback
```

Рекомендуемые адреса прослушивания:

```text
/ip4/0.0.0.0/tcp/4001
/ip4/0.0.0.0/udp/4001/quic-v1
```

При работе в приватной сети адреса могут быть ограничены внутренней сетью.

## 7.2. Шифрование

Весь межузловой трафик должен шифроваться.

Рекомендуемый протокол:

```text
Noise
```

Не допускается передача задач, результатов и служебных сообщений в открытом виде вне локального тестового режима.

## 7.3. Аутентификация

Каждый узел должен аутентифицировать другой узел по `Peer ID`.

Дополнительно должны поддерживаться:

- списки разрешенных пиров;
- списки запрещенных пиров;
- минимальный уровень доверия.

## 7.4. Протоколы прикладного уровня

Для обмена задачами должны использоваться отдельные протокольные идентификаторы.

Пример:

```text
/picomesh/task/0.1.0
/picomesh/discovery/0.1.0
/picomesh/membership/0.1.0
/picomesh/capability/0.1.0
/picomesh/control/0.1.0
```

## 7.5. Формат сообщений

Рекомендуемый формат:

```text
Protocol Buffers version 3
```

Допускается JSON для административного API, но для меж узлового обмена рекомендуется Protobuf.

---

## 8. Требования к обнаружению и маршрутизации

## 8.1. Локальный поиск

Требования:

1. Узлы на одном сервере должны обнаруживаться автоматически.
2. Локальный поиск не должен требовать доступа в Интернет.
3. Локальные соединения должны использовать Unix socket или loopback.

## 8.2. Поиск в локальной сети

Требования:

1. Узлы должны анонсировать себя через mDNS.
2. Узлы должны автоматически находить другие узлы в той же подсети.
3. Обнаруженные узлы должны проходить криптографическую аутентификацию перед добавлением в соседи.

## 8.3. Поиск в глобальной сети

Требования:

1. Новый узел должен подключаться через один или несколько известных адресов.
2. После подключения узел должен получать список доступных соседей.
3. Узел должен публиковать собственные навыки в DHT.
4. Узел должен уметь искать другие узлы по навыкам через DHT.
5. Система должна поддерживать деградацию при недоступности DHT.

## 8.4. Маршрутизация задач

Маршрутизация должна быть:

- распределенной;
- ограниченной по TTL;
- защищенной от циклов;
- учитывающей навыки;
- учитывающей нагрузку;
- защищенной от шторма сообщений.

---

## 9. Требования к хранению данных

## 9.1. Локальное хранилище

Каждый узел должен хранить локальные данные в отдельном каталоге.

Рекомендуемая структура:

```text
/var/lib/picomesh/
├── keys/
├── config/
├── peers/
├── tasks/
├── artifacts/
├── logs/
└── audit/
```

## 9.2. Хранилище задач

Узел должен хранить минимальный журнал задач.

Для каждой задачи сохраняются:

- идентификатор;
- статус;
- отправитель;
- получатель;
- время получения;
- время завершения;
- результат или код ошибки;
- хеш результата;
- подпись.

Полное тело задачи может не храниться, если это запрещено политикой приватности.

## 9.3. Хранилище артефактов

Артефакты выполнения задач должны храниться локально.

Рекомендуемая адресация:

```text
sha256(content)
```

Пример:

```text
/var/lib/picomesh/artifacts/sha256/ab/cd/abcd...
```

## 9.4. Очистка данных

Должна поддерживаться автоматическая очистка:

- временных рабочих каталогов;
- старых артефактов;
- старых журналов задач;
- кеша дедупликации.

Рекомендуемый срок хранения временных данных:

```text
7 дней
```

## 10. Требования к интеграции с PicoClaw

## 10.1. Модель интеграции

Интеграция должна выполняться через отдельный адаптер.

Адаптер должен:

1. Управлять процессом PicoClaw.
2. Передавать задачи в PicoClaw.
3. Получать результат.
4. Контролировать таймауты.
5. Управлять рабочими пространствами.
6. Передавать ограничения и разрешения.

## 10.2. Способы интеграции

Допускаются следующие способы:

1. Вызов локального HTTP API PicoClaw.
2. Вызов CLI-команд PicoClaw.
3. Запуск процесса и обмен через стандартные потоки.
4. Встроенная библиотека, если это доступно.

Приоритет должен отдаваться наиболее стабильному и изолированному способу.

## 10.3. Конфигурация PicoClaw

Для каждого узла должны задаваться:

- путь к бинарному файлу PicoClaw;
- путь к конфигурации;
- рабочая директория;
- переменные окружения;
- список разрешенных навыков;
- модельные параметры;
- ограничения ресурсов.

Пример:

```yaml
picoclaw:
  binary: /usr/local/bin/picoclaw
  config: /etc/picoclaw/config.json
  workspace_root: /var/lib/picomesh/picoclaw/workspaces
  timeout_seconds: 600
  max_concurrent_agents: 4
  env:
    OPENAI_API_KEY_FILE: /run/secrets/openai_api_key
```

## 10.4. Локальная мультиагентность

Узел может запускать несколько локальных агентов PicoClaw.

В этом случае адаптер должен:

- назначать каждому локальному агенту отдельное рабочее пространство;
- маршрутизировать задачи по навыкам;
- контролировать параллельность;
- изолировать секреты.

## 11. Требования к безопасности

## 11.1. Минимальные требования

Система должна обеспечивать:

1. Шифрование трафика.
2. Аутентификацию узлов.
3. Подпись задач.
4. Контроль доступа к навыкам.
5. Ограничение частоты запросов.
6. Защиту от повторного воспроизведения.
7. Журналирование событий безопасности.

## 11.2. Управление ключами

Требования:

1. Приватный ключ не должен передаваться по сети.
2. Приватный ключ не должен попадать в логи.
3. Должна поддерживаться ротация ключей.
4. При компрометации ключа узел должен иметь возможность отозвать старый идентификатор через административную процедуру.

## 11.3. Политика доверия

Система должна поддерживать уровни доверия:

```text
trusted
known
limited
untrusted
blocked
```

Уровень доверия должен влиять на:

- прием задач;
- делегирование задач;
- доступ к навыкам;
- обмен списками соседей.

## 11.4. Ограничение опасных операций

По умолчанию должны быть запрещены:

- выполнение произвольных команд оболочки;
- доступ к хостовой файловой системе вне рабочей директории;
- исходящий сетевой доступ, если он не требуется;
- чтение секретов узла;
- изменение конфигурации другим узлом.

Опасные операции должны включаться только явно.

## 11.5. Защита от злоупотреблений

Система должна защищаться от:

- спама задачами;
- бесконечных циклов;
- чрезмерного делегирования;
- подмены задач;
- подмены результатов;
- истощения ресурсов;
- отравления таблицы соседей.

Для этого должны применяться:

- rate limiting;
- TTL;
- дедупликация;
- лимиты на размер сообщений;
- лимиты на размер артефактов;
- репутационные метрики.

## 16. Требования к производительности и масштабируемости

Ниже приведены целевые показатели для первой версии системы.

### 16.1. Масштаб

Система должна стабильно работать при:

```text
100 узлов
1000 узлов в режиме деградации без потери базовой маршрутизации
```

### 16.2. Потребление ресурсов

На узле без активной задачи:

```text
mesh daemon RAM: до 128 МБ
запуск узла: до 10 секунд
```

При активной задаче потребление зависит от PicoClaw и используемых моделей.

### 16.3. Сетевые задержки

Целевые значения при нормальной сети:

```text
обнаружение локального соседа: до 2 секунд
обнаружение соседа в LAN: до 10 секунд
подключение к удаленному узлу: до 30 секунд
передача задачи соседу: до 2 секунд без учета времени выполнения
```

### 16.4. Ограничение служебного трафика

Служебный gossip-трафик не должен приводить к насыщению канала при штатной работе.

Рекомендуемый предел служебного трафика на узел:

```text
до 100 Кбит/с в режиме простоя
до 1 Мбит/с при активной маршрутизации
```

## 17. Требования к тестированию

## 17.1. Модульные тесты

Должны быть покрыты:

- валидация задач;
- подпись сообщений;
- работа с таблицей соседей;
- локальное хранилище;
- обработка ошибок;
- дедупликация.

## 17.2. Интеграционные тесты

Должны проверяться сценарии:

1. Два узла обнаруживают друг друга локально.
2. Три узла образуют сеть.
3. Задача отправляется на узел А и выполняется узлом Б.
4. Результат возвращается узлу А.
5. Узел падает во время задачи.
6. Задача делегируется через промежуточный узел.
7. Повторная отправка той же задачи не вызывает повторное выполнение.
8. Задача с истекшим TTL не распространяется бесконечно.

## 17.3. Нагрузочное тестирование

Необходимо смоделировать:

```text
100 узлов
500 узлов
1000 узлов в симуляции
```

Проверяются:

- стабильность членства;
- скорость обнаружения;
- уровень служебного трафика;
- время маршрутизации задачи;
- поведение при падении 10% узлов.

## 17.4. Тесты безопасности

Необходимо проверить:

1. Узел без подписи не может отправить задачу.
2. Задача с измененным содержимым отклоняется.
3. Неизвестный узел не получает задачи при политике `limited`.
4. Заблокированный узел не может подключиться.
5. Реле не может расшифровать содержимое задачи.
6. Превышение лимита запросов приводит к отклонению.

## 20. Критерии приемки

Система считается прошедшей приемку, если выполняются следующие условия:

### 20.1. Функциональная приемка

1. Узел успешно запускается и генерирует идентификатор.
2. Узел подключается к сети через локальный поиск или bootstrap.
3. Узел видит соседей.
4. Задача может быть отправлена на любой узел.
5. Задача может быть выполнена другим узлом.
6. Результат возвращается инициатору.
7. Подзадачи могут делегироваться соседям соседей.
8. TTL предотвращает бесконечное распространение.
9. Падение одного узла не приводит к остановке сети.
10. Система корректно обрабатывает повторную отправку задачи.

### 20.2. Приемка по безопасности

1. Подписи задач проверяются.
2. Неавторизованные узлы не могут выполнять привилегированные операции.
3. Трафик между узлами зашифрован.
4. Секреты не передаются между узлами.
5. Опасные навыки отключены по умолчанию.

### 20.3. Приемка по масштабу

1. Система работает в тестовой сети из не менее чем 100 узлов или 100 эмулированных узлов.
2. Служебный трафик не превышает установленных пределов.
3. Задачи маршрутизируются без образования устойчивых циклов.
4. Система сохраняет работоспособность при отключении не менее 10% узлов.

## 21. Риски и меры снижения

### 21.1. Риск: сложность полностью децентрализованной маршрутизации

**Меры:**

- начать с гибридной модели;
- ограничить TTL;
- использовать кеш навыков;
- применять репутационные метрики.

### 21.2. Риск: нестабильность узлов за NAT

**Меры:**

- использовать relay-узлы;
- использовать WireGuard/Tailscale;
- предпочитать прямые соединения.

### 21.3. Риск: чрезмерный служебный трафик

**Меры:**

- ограничить частоту gossip;
- агрегировать обновления;
- использовать сжатие;
- ограничить размер сообщений.

### 21.4. Риск: выполнение вредоносных задач

**Меры:**

- политики доверия;
- изоляция рабочих пространств;
- запрет опасных операций по умолчанию;
- лимиты ресурсов.

### 21.5. Риск: недостаточная готовность PicoClaw к внешней автоматизации

**Меры:**

- реализовать адаптер;
- использовать несколько способов интеграции;
- изолировать взаимодействие с PicoClaw внутри узла.

# Приложение C. Пример сценария прохождения задачи

```text
1. Пользователь отправляет задачу на узел A.
2. Узел A проверяет подпись, TTL и формат задачи.
3. Узел A оценивает собственные навыки.
4. Узел A не имеет нужного навыка.
5. Узел A проверяет соседей.
6. Узел A находит узел B с подходящим навыком.
7. Узел A передает задачу узлу B.
8. Узел B принимает задачу.
9. Узел B понимает, что нужна подзадача.
10. Узел B создает подзадачу и делегирует ее узлу C.
11. Узел C выполняет подзадачу через PicoClaw.
12. Узел C возвращает результат узлу B.
13. Узел B завершает основную задачу.
14. Узел B возвращает результат узлу A.
15. Узел A возвращает итоговый результат пользователю.
```

# Приложение E. Минимальный набор приемочных испытаний

1. **Запуск одного узла**
   - узел стартует;
   - генерирует ключ;
   - открывает административный порт только локально;
   - успешно выполняет локальную задачу через PicoClaw.

2. **Обнаружение двух узлов в одной сети**
   - узлы находят друг друга;
   - устанавливают соединение;
   - обмениваются возможностями.

3. **Делегирование задачи**
   - задача отправляется на узел без нужного навыка;
   - задача делегируется соседу;
   - результат возвращается.

4. **Многопрыжковая маршрутизация**
   - задача проходит минимум через два узла;
   - маршрут сохраняется;
   - результат возвращается по маршруту.

5. **Отказоустойчивость**
   - один из узлов отключается;
   - сеть продолжает работать;
   - задачи не теряются или корректно помечаются как ошибочные.

6. **Безопасность**
   - поддельная задача отклоняется;
   - неизвестный узел не получает доступ к выполнению;
   - секреты не передаются по сети.

## Итоговое положение

Настоящее техническое задание описывает разработку полностью децентрализованной агентной P2P-сети на базе **PicoClaw**, в которой:

- каждый узел автономен;
- задача может войти через любой узел;
- исполнители ищутся среди соседей и соседей соседей;
- сеть не требует обязательного центрального координатора;
- безопасность обеспечивается криптографической идентификацией, подписями и шифрованием;
- масштабируемость достигается за счет gossip, DHT и ограниченного делегирования;
- эксплуатационная готовность обеспечивается Docker, Ansible, Prometheus и структурированными логами.
