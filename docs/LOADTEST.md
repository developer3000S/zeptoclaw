# Нагрузочное тестирование: симуляция membership/routing (ТЗ 17.3, 22 п.6, 16.4)

Документ — отчёт о прогоне `internal/simulator`: тот же протокол membership и
маршрутизации, что исполняет узел, на сетях 100 / 500 / 1000 узлов. Разбор —
[ТЗ.md](../ТЗ.md) §16.4, §17.3, §22 п.6; пакет описан в
[`internal/simulator/doc.go`](../internal/simulator/doc.go); место в общем
статусе — [STATUS.md](STATUS.md).

Таблицы этого документа воспроизводятся из прогонов, а не переписываются от руки:
весь markdown печатает `Markdown()` из `report.go`, и копия актуального отчёта
лежит в `load-test-output.txt` (его создаёт сам `make test-load` через `tee`;
файл в `.gitignore`). Здесь перенесены ключевые строки и добавлены прогоны,
которые не влезли в один запуск.

---

## Как воспроизвести

```bash
export PATH=$PATH:/usr/local/go/bin:/root/go/bin
make test-load            # 100 / 500 / 1000 узлов, → load-test-output.txt
```

`make test-load` — нес модифицированная цель Makefile (строки 128–130):

```
$(GO) test $(GOFLAGS) -tags=load -timeout 60m -run TestLoadSim -v ./internal/simulator/... \
  | tee load-test-output.txt
```

Быстрые инварианты модели (секунды, без тега `load`, идут в `make test`/`make ci`):

```bash
go test -count=1 ./internal/simulator/...
```

Настройки прогона — переменные окружения (значения по умолчанию совпадают с
таблицей ниже): `ZETOMESH_SIM_SIZES`, `ZETOMESH_SIM_STEPS` (`idle:active:failure`
в heartbeat), `ZETOMESH_SIM_SEED`, `ZETOMESH_SIM_CRASH`, `ZETOMESH_SIM_REPORT`,
`ZETOMESH_SIM_SYNC_NODES` (размеры сети для замера границы модели, §«Границы»).

Сноска к 1000 узлов: покой измерен отдельным прогоном с расписaniem 40:1:1
(то есть idle-фаза та же, 40 heartbeat, но без активной фазы и отказа) — на 24-й
минуте он не закончился; по трёхточечной экстраполяции 21-битного прогона
(4989.8 Кбит/с) и 40-битного 500-узлового (8388.8) порядок величины — 2–3 · 10³
Кбит/с на узел, то есть **НЕ выполнено** с тем же запасом в разы, что и при 500.
Число помечено как оценка, а не как измерение: точного замера «40 heartbeat на
1000 узлов» в этом отчёте нет.

Ни один из трёх размеров не уложился в норматив ТЗ 16.4. Параметры не
подгонялись: цель прогона — измерить, а не пройти.

### Маршрутизация задач

| | 100 | 500 |
|---|---:|---:|
| Время маршрутизации p50 / p95 / p99, с | 2 / 3 / 3 | 2 / 3 / 3 |
| Hops до исполнителя, среднее | 0.79 | 0.79 |
| Задач: инжектировано / локально / делегировано / без исполнителя / потеряно | 1400 / 296 / 1103 / 0 / 1 | 7000 / 1449 / 5488 / 55 / 63 |

Квант времени — beat 3 s (модель не знает channel-задержки), поэтому «2 с»
означает «один tick», а не разрешение в секунды. Решение принимает настоящий
`routing.Table.Select` с весами 0.40/0.25/0.20/0.10/0.05 и фильтром навыков;
кандидат, которому ушла бы задача на реальном узле, — тот же кандидат.

### Отказ 10 % узлов

| | 100 | 500 |
|---|---:|---:|
| Связность графа: покой → минимум при отказе → конец фазы | 1.0000 → 1.0000 → 1.0000 | 1.0000 → **0.7902** → 1.0000 |
| Восстановление views после отказа p50 / p95 / max, heartbeat | 5.0 / 5.0 / 5.0 | 5.0 / 5.0 / 5.0 |
| Сходимость после отказа (полнота / свежесть), heartbeat | 0.0 / 0.0 | не достигнуто / 0.0 |
| Записей views: принято впервые / выбыло по expiry | 9900 / 900 | 14983244 / 14781334 |
| Причины потерь задач | worker crashed: 1 | no eligible peers reachable: 55; worker crashed: 8 |

Отказ — тихая потеря heartbeat: узел не шлёт «left»; сосед узнаёт о нём только
тем, что состояние перестало обновляться, и expiry наступает через
`failure_timeout` = 5 heartbeat — ровно то, что измеряет строка
«восстановление views». Связность не падает ни при каком размере (при 500 —
до 0.79 на минимуме и восстанавливается до 1.0), то есть граф не рассыпается.
При 500 узлах 55 задач не нашли исполнителя: у 10 % умерших узлов были навыки,
которые никем больше не заявлены в пределах досягаемости `known`-множества —
это содержательный результат, а не поломка симуляции.

## Границы модели

Полный раздел печатает отчёт («Что модель воспроизводит / Что модель НЕ
воспроизводит / Границы, о которых надо знать, читая таблицу» + «Границы в
числах»). Здесь — то, что меняет чтение цифр выше.

**Модель НЕ воспроизводит:** TCP/TLS(noise)-рукопожатие и стоимость соединения;
NAT/relay/дыры; пропускную способность, задержку, джиттер, потери канала
(доставка дискретна: одно ребро = один тик); backpressure и насыщение; CPU,
память, диск, GC реального узла (из machine numbers есть только стоимость самого
прогона — wall clock и VmHWM процесса теста); connmgr; реальный LLM и реальный
профиль нагрузки; DHT-обход целиком; криптооперации (подписи учтены в размере,
но не считаются). Там, где метрика не измерима, в отчёте стоит «не измеряется
данной моделью», а не оцененное число.

Отсутствие backpressure — причина, по которой провал «провал и в реальности», а
близость к потолку — не «в реальности всё будет хорошо»: реальный узел у предела
начнёт терять и откладывать, а не платить ровно столько же.

### Границы в числах: аналитическая ретрансляция full-sync

Реструктуризация, сделанная в этом пакете, считает **дальнейшую ретрансляцию
пачки full-sync аналитически** (одна копия на подписчика), а не точным обходом
флуда: при 8636-байтной пачке включён IDONTWANT, а обход стоил бы Θ(N²)
доставок на beat. Первый хоп каждой пачки обходится дословно. Это самая
нагруженная замена в модели, и её погрешность измерена на трёх размерах сети
(тот же seed, idle-фаза 21 heartbeat; строки `TestFullSyncAnalyticVersusExactFlood`
и прогона под тегом `load`):

| Узлов | Байт full-sync: аналитика | точный обход | расхождение | Кбит/с на узел за прогон: аналитика | точный обход | расхождение | Полнота views: аналитика | точный обход | расхождение |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 60 | 56 541 942 | 56 982 300 | −0.77 % | 213.0 | 214.5 | −0.70 % | 59.0 | 59.0 | +0.00 % |
| 150 | 903 446 302 | 908 210 279 | −0.52 % | 921.2 | 929.3 | −0.87 % | 149.0 | 149.0 | +0.00 % |
| 300 | 6 120 910 389 | 3 873 820 531 | **+58.01 %** | 2751.1 | 1891.8 | **+45.43 %** | 229.5 | 260.5 | **−11.88 %** |

Читать надо так, и это единственная честная формулировка:

* Погрешность **не мала и не постоянна**. При 60 и 150 узлах она меньше
  процента; при 300 она +58 % по байтам и +45 % по трафику на узел. Знак
  меняется по ходу: допуск то занижает, то завышает расход. Ссылаться в отчёте
  на «−0.77 %» как на оценку погрешности при 500 или 1000 узлах нельзя.
* На **состав** замена влияеть только на большом размере: до 150 узлов
  полнота views не меняется вовсе (+0.00 %), при 300 расходится на −11.88 %
  (229.5 записей против 260.5). Причина видна в строке «Полнота views
  0.639 (319 из 499)» в таблице результатов: аналитика не доносит содержимое
  пачки, и состав держится только на heartbeat-публикациях, которые обходятся
  точно, — пока view не начнёт упираться в expiry.
* На **вердикт по ТЗ 16.4** это не влияет ни при каком замеренном размере:
  превышение потолка измеряется разами (6.8×, 83.9×), а не процентами. Влияет
  на наклон: аналитика завышает и уровень, и рост, поэтому степень роста
  служебного приёма надо смотреть не по границе 5, а по строке «он же,
  делённый на N» в отчёте.

Сравнение сознательно не разбито по фазам: точный обход доносит хвост флуда за
границу фазы, а аналитика ставит все копии пачки в beat самой пачки, — по
фазам эти два способа расходятся сильнее, чем за прогон целиком, и сравнивать их
по фазам некорректно.

### Прочие границы, влияющие на таблицу результатов

1. **Дедупликация подавляет копию на стороне отправителя** (gossipsub пишет оба
   экземпляра в один RPC-кадр тому же пиру). Реальный роутер доставит дубликат и
   отбросит его принявшим узлом — на один кадр больше. Разница ограничена числом
   треугольников в mesh степени D и только занижает трафик; счётчик подавленных
   копий в отчёте — 5.2 · 10⁶ при 100 узлах, 1.1 · 10⁸ при 500 (в разах от числа
   доставок: 4.07 и 3.64 — копий подавляется больше, чем было доставок, потому что
   на одну доставку приходится несколько запоздавших отправителей).
2. **Служебный приём на узел растёт быстрее линейного**: делённый на N даёт 6.8
   при 100 узлах и 16.8 при 500, показатель степени ≈ 1.7. Механизм (каждый узел
   платит за каждую публикацию каждого узла) — свойство дизайна топика; степень
   — следствие того, что с шириной сети растёт и число пачек full-sync на beat.
3. **Каталог навыков гетерогенен** (5 %+5 % из `DefaultParams`) — это нагрузка, а
   не факт протокола: «general» у всех узлов удовлетворял бы
   `routing.skillsMatch`, и любая задача решалась бы в один хоп.
4. **Байты — `proto.Marshal` настоящих сообщений**, но crypto не исполняется.

## Что это значит для ТЗ 16.4

Норматив не выполнен ни при одном размере и не выполняется монотонно по мере
роста сети. Измеренный механизм отвода за потолок: `PublishFull` раз в
`full_sync` шлёт весь view пачками по 32 состояния, и при N узлов каждый узел
получает по ним копию от каждого достижимого издателя — 85–86 % служебного
трафика в покое при 500 узлах (7191.5 из 8388.8 Кбит/с).

Это вывод про протокол, а не про симуляцию: замена точного обхода на
аналитику ошибается на доли процента там, где вердикт уже «НЕ выполнен» в разы,
а при 300 узлах она завышает расход — то есть реальный флуд был бы дешевле, чем
показывает модель, но не на порядки, а на десятки процентов. Чтобы утверждать
обратное, нужен замер, которого в этом отчёте нет: точный обход full-sync при
1000 узлах.
